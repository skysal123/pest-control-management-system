  🔐 Phase 2: Login Flow (/auth/login)

  File: blueprints/auth.py:26

  When you visit /auth/login:

  1. auth.login() checks if already logged in → redirects by role
  2. Renders login.html form

  When you submit email + password:

  1. Browser sends POST /auth/login
  2. Backend validation:
    - Lowercase the email
    - Query: User.query.filter(db.func.lower(User.email) == email).first()
  3. Password check:
    - user.check_password(password) uses werkzeug.security.check_password_hash()
    - Compares hash with stored password_hash (bcrypt/argon)
  4. Active check:
    - If is_active=False → flash warning, deny login
  5. login_user(user, remember=remember) — Flask-Login creates session cookie
  6. _role_redirect(user):
    - ADMIN → /admin/
    - TECHNICIAN → /technician/

  Session persistence:
  - @login_manager.user_loader in app/__init__.py reloads User from DB on each
  request via session cookie

  Warranty Management (/admin/warranties)

  File: blueprints/admin.py:417 + warranty.py

  What you see:

  1. Table of all completed bookings
  2. For each booking:
    - warranty_end = completed_at + WARRANTY_DAYS (90 days)
    - days_left = (warranty_end - now).days
    - Status: "Active" (green) or "Expired" (grey)
    - Reminders sent: badge showing count from warranty_reminders table

  How reminders work:

  1. Daily cron runs python -m warranty
  2. warranty.scan_and_notify(app):
    - Loads all bookings with completed_at IS NOT NULL
    - For each booking, checks if warranty expiry is within reminder window
    - Reminder offsets: [7, 1] days before expiry
    - Checks _already_reminded(booking_id, days_before) — queries
  warranty_reminders table
    - If not already sent:
        - Calls notify_warranty_reminder(b, days_left) → sends email
      - Logs WarrantyReminder row to prevent duplicates
      - In-app notifications to all admins

  �️ Database Schema Summary

  Tables & Relationships

  users (id, name, email, password_hash, role, is_active, created_at)
    ↓ (technician_id)
  bookings
    ↓ (customer_id) → customers
    ↓ (service_id)  → services
    ↓ (lead_id)     → leads → customer_id → customers
    ↓ (feedback)    → feedback → technician_id → users

  notifications (id, user_id, type, message, link, status, created_at)
  warranty_reminders (id, booking_id, sent_at, days_before, customer_email)

  Key Models (models.py)

  User — admin + technician auth
  - set_password(raw) — hashes with werkzeug
  - check_password(raw) — verifies hash
  - is_admin / is_technician — role checks

  Customer — created from enquiries or manual bookings
  - Identified primarily by phone number (finds-or-creates pattern)

  Service — pest control offerings
  - faq_list property — parses FAQ text into accordion format
  - icon — Bootstrap Icons class

  Lead — enquiry tracker
  - Statuses: New, Contacted, Follow-up Required, Booking Created, Closed,
  Cancelled
  - Sources: Website, WhatsApp, Phone Call, Referral
  - One-to-one with Booking (when converted)

  Booking — confirmed service
  - Statuses: Pending, Confirmed, Assigned, In Progress, Completed, Cancelled
  - warranty_end property: completed_at + WARRANTY_DAYS
  - is_under_warranty property: warranty_end >= now

  Feedback — post-service rating
  - Unique per booking (unique=True on booking_id)
  - 1-5 star rating + comments

  Notification — in-app alert
  - Linked to user_id (admin or technician)
  - Types: booking_created, technician_assigned, service_completed,
  warranty_reminder

  WarrantyReminder — log to prevent duplicate sends
  - Composite key: (booking_id, days_before)

  🔄 Complete Customer Journey

  1. Customer visits homepage
     → Sees services, clicks "Request Enquiry"
     → Fills form on /contact
     → Backend creates Customer + Lead (status="New")

  2. Admin logs in
     → Dashboard shows new lead count
     → Opens lead, updates status to "Contacted"
     → Calls customer, agrees on date

  3. Admin clicks "Convert to Booking"
     → Booking form pre-filled with customer info
     → Admin selects service, date, time, technician
     → Backend creates Booking (status="Assigned")
     → Triggers notify_booking_created + notify_technician_assigned
     → Customer receives confirmation email
     → Technician receives email + in-app notification

  4. Technician logs in
     → Dashboard shows assigned job
     → Opens job, clicks "Start Service"
     → Backend sets status="In Progress"

  5. Technician completes service
     → Clicks "Mark Completed" (with optional notes)
     → Backend sets status="Completed", completed_at=now
     → Triggers notify_service_completed
     → Customer receives email: "Thank you! Share feedback"

  6. Customer clicks feedback link
     → /feedback/<booking_id>
     → Submits 5-star rating + comment
     → Backend creates Feedback row
     → Admin sees in feedback dashboard
     → Home page testimonials update

  7. 83 days later (7 days before 90-day warranty expiry)
     → Daily cron runs warranty.scan_and_notify
     → Finds booking's warranty ends in 7 days
     → Checks warranty_reminders table (not sent yet)
     → Sends email to customer: "Warranty expires in 7 days"
     → Logs WarrantyReminder row
     → Admin gets in-app notification

  8. 89 days later (1 day before expiry)
     → Cron runs again
     → Sends second reminder: "Warranty expires tomorrow"

  9. Customer renews service
     → Books new service via /contact
     → Cycle repeats

  📝 Key Design Patterns

  1. Finds-or-creates customer — by phone number (same customer may enquire
  multiple times)
  2. PRG (Post-Redirect-Get) — POSTs redirect to GET to prevent form
  resubmission
  3. Role-based access control — _admin_required and _tech_required decorators
  4. Status state machines — Lead status and Booking status have defined
  transitions
  5. Warranty as computed property — warranty_end = completed_at + WARRANTY_DAYS
  (not stored, always fresh)
